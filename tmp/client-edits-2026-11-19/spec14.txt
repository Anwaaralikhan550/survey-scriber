1. Executive summary
SurveyScriber will add a secure browser-based editor, accessed through a single live editing link for each report. The same link may
be shared with colleagues for sequential editing and review. The browser edits the structured SurveyScriber report data in the cloud;
it is not a Microsoft Word round-trip workflow.
The implementation extends the existing Flutter, NestJS, Prisma and PostgreSQL system. It preserves offline-first mobile operation
and keeps final PDF and Word generation inside the Flutter app. The server does not render reports.
• Original inspection report: immutable snapshot of what was originally generated, including original documents and structured data.
• Current edited report: one working copy. Successful saves update this copy; a lightweight field-level audit records amendments. No
competing edited branches.
• Final report: owner-approved edited report, regenerated by the existing Flutter phrase engine and ReportBuilder.
• Completed reports remain in cloud for 60 days from finalisation. Abandoned drafts are purged after 30 days of inactivity, following
warnings.
• Surveyors are responsible for long-term retention. SurveyScriber provides a complete archive download and later restoration.

Report structure comes from published JSON trees: `assets/property_inspection/inspection_tree.json` (Home Survey) and
`assets/property_valuation/valuation_tree.json` (Valuation). Phrase banks contain approximately 1,256 inspection phrases and 495
valuation templates. The admin portal publishes versioned definitions through `v2_tree_versions`, with rollback and audit. Stable
UUIDs are used; newer tree IDs are deterministic from survey/screen/field.
2.2 Existing report generation and sync
The phone generates reports offline: saved answers + tree + phrase bank pass through the phrase engine; ReportBuilder lays out
sections, tables, photos and signatures; separate renderers produce PDF and Word. The server stores the uploaded PDF and
returns report data, but does not render reports.
• Offline-first: phone changes enter `sync_queue` and push when online.
• `POST /sync/push` sends batches with idempotency keys; entities include survey, section and answer.
• Photos upload separately through `/media/upload`.
• `GET /sync/pull` uses a timestamp cursor and includes deletions.
• Current conflicts are last-write-wins on the server; the phone avoids overwriting items with unsent local changes; no field-level merge.
• Existing reusable facilities: hashed single-use client magic-link tokens, audit log table, role system, survey status workflow and
`baseVersion`/HTTP 409 for tree publishing.
The current survey status flow is Draft, In progress, Completed, Pending review, Approved and Rejected. The remote-editor workflow
must be mapped carefully rather than casually changing existing status semantics.
3. Product scope and design principles
3.1 In scope
• Browser editor for desktop/laptop and supported iPad browsers; no installation.
• One active edit link per report, expiring after 72 hours; link can be shared for sequential work.
• Edit supported report narratives, answers, ratings, recommendations, property details and stable paragraph blocks.
• Add, replace, caption, delete, reorder and section-associate photographs.
• Autosave, explicit save/synchronise feedback, version checks and conflict recovery.
• AI suggestions with explicit accept/reject; review and owner approval; finalise, lock and controlled reopen.
• Immutable original snapshot, one current edited report, lightweight field-level audit, archive export/import and retention jobs.
3.2 Out of scope for initial release
• Word import/edit/re-upload workflow; server-side PDF/DOCX rendering; full live PDF preview.
• Multiple competing edited branches; automatic AI approval, ratings or finalisation.
• Paid extended cloud retention; mandatory OneDrive/Google Drive/S3 integration.
3.3 Non-negotiable principles
• Extend existing Survey, Section, Answer and Media records; avoid a parallel report database.
• Original is immutable; edited report is one current working copy.
• Reject stale writes; do not use last-write-wins for remote editing.
• Only owner/authorised owner role creates or revokes links, approves, finalises or reopens.

5. Two-report-state architecture
5.1 Original inspection report – immutable
When the original report is generated on the phone, capture an immutable snapshot representing the report as generated at that
time. It must not be changed by desktop editing, later phone sync or finalisation.
• Original PDF and original DOCX.
• Original header, sections, answers, generated text, ratings, recommendations and property details.
• Original photographs, captions/order and signature records/media required to evidence the original.
• Inspection/valuation tree version and phrase-bank version used.
• Survey UUID, generation timestamp, owner UUID, app/build version where available, and checksums.
Implementation note: Current confirmation explicitly says the server stores uploaded PDF. It does not confirm that DOCX is
uploaded/stored. Original DOCX cloud storage is therefore a new requirement to verify against mobile upload code.
5.2 Current edited report – one working copy
Create one editable working copy from the original snapshot. All accepted edits update this same copy and increment
`reportVersion`. Audit events and technical checkpoints may be retained, but users must not see competing edited branches. Use
existing stable UUIDs; add stable block UUIDs where paragraphs are not already represented by stable fields.

7. Secure edit-link lifecycle
• Owner-only creation/revocation (or explicitly authorised role under business rules).
• One active link per report, expiring exactly 72 hours after creation.
• Same link may be forwarded and used sequentially during validity.
• New link only after prior link expires, is revoked/cancelled or invalidated.
• Finalisation revokes link and sessions.
• Link creation and one-active-link rule enforced transactionally and by database constraint.
Generate a cryptographically secure high-entropy token; store only a one-way hash. Never log raw token. Require HTTPS, rate
limits, server-side expiry/revocation/report-state checks and short-lived editor session after token exchange. Use secure cookie
practices where feasible, restrictive referrer policy, no indexing and no third-party scripts on token pages.
Identity limitation: a forwarded bearer link does not identify the human holding it. If named reviewer attribution is required, require
sign-in or verified identity. Otherwise audit the actor as a link session, not a named person.
POST /api/reports/:surveyId/edit-links
  authenticate owner
  begin transaction; lock survey row
  reject if an active link exists
  generate random token; store hash
  expiresAt = now + 72 hours
  return URL once to owner
GET /api/editor/link-exchange?token=...
  validate hash, expiry, revocation and report state
  exchange for short-lived editor session
DELETE /api/reports/:surveyId/edit-links/:linkId
  owner authentication; revoke link and sessions

10. Save, versioning and conflicts
Add monotonically increasing integer `reportVersion` for the edited state. The current system has only an updated-at timestamp for
reports. Use optimistic concurrency and return HTTP 409 for stale writes.
PATCH /api/editor/reports/:surveyId
{
  "baseVersion": 12,
  "idempotencyKey": "client-generated-uuid",
  "changes": [
    {"entityType":"Answer","entityId":"uuid",
     "field":"value","value":"updated value"}
  ]
}
Success: {"reportVersion":13,"savedAt":"ISO-8601"}
Stale: HTTP 409
{"code":"REPORT_VERSION_CONFLICT","currentVersion":13}
• Validate editor session, report state, baseVersion, idempotency key and field values.
• Write content changes and field-level audit events in one transaction; increment version once per accepted batch.
• Reject stale writes. Never silently overwrite.
• Retain unsaved browser changes after 409; fetch latest cloud state and provide safe reconciliation.
• Apply version checks to relevant mobile `/sync/push` mutations for remotely edited surveys too.
• Preserve existing sync idempotency keys and local queue behaviour; do not silently discard phone-side unsent changes.
• Autosave with debounce, bounded exponential retry for transient failures, and visible Saving/Saved/Offline/Conflict/Error states. Do
not retry 409 as a transient error.

13. AI assistance
AI is advisory only. It may improve grammar/professional wording, expand surveyor notes without adding facts, clarify
recommendations and flag contradictions or missing information. Every suggestion must be presented for explicit accept/reject.
AI must never invent defects, measurements, test results, photographs, access conditions or observations; automatically change
ratings; make unapproved professional judgements; approve or finalise reports. Accepted changes go through the same
version-checked save API and are audited as AI-assisted changes accepted by the user. Rejected suggestions do not change report
data.

Meaningful activity means a successful content save or defined authorised workflow action; merely opening a report should not reset

15.3 Purge safeguards
• Warnings through app and registered email where available; archive download remains available before deletion.
• Use idempotent deletion queue with operational retry/grace for failed file deletion; this is not a user-selectable retention extension.
• Support documented legal/complaint hold where required.
• Delete associated report content, media, original/final files and archive copies under the policy.
• Retain only minimal justified operational deletion metadata (identifier/tombstone, date, policy reason, job outcome); no substantive
report contents.
• Document backup expiry so deleted data is not retained indefinitely in recoverable backups.
These are product policies, not a legal determination of surveyors' professional record-retention obligations. User terms, privacy
notices and onboarding must clearly explain the surveyor's long-term retention responsibility.
16. File storage and deployment

root; use generated UUID storage keys; validate content; write atomically; verify size/checksum; authorise all reads; monitor disk

PostgreSQL stores structured records, metadata, storage keys, checksums and retention state—not binary photos, PDF, DOCX or
ZIP content. Future private object storage is optional and not a first-release dependency.

18. Security, privacy and audit
• HTTPS/TLS at nginx; helmet/security headers; restrictive CORS; referrer policy no-referrer; no indexing.
• Hash tokens at rest; never log raw tokens; rate-limit token exchange, login and uploads.
• Short-lived editor session; revoke on link expiry/revocation/finalisation; server-side permission check on every operation.
• Use CSRF protection if cookie-based sessions; secure cookies; validate DTOs and file content.
• Protect against path traversal, ZIP bombs, malformed archives, oversized uploads and unauthorised file reads.
• Field-level audit records survey, reportVersion, entity/field, before/after, actor/session, source and timestamp.
• Audit link lifecycle, media changes, AI accept/reject, review, approval, finalise/reopen, archive export/import, warnings and purge.
• Do not overstate identity when bearer link is forwarded; use reviewer authentication for named attribution.
Avoid logging secrets or unnecessary sensitive report content. Define access and retention for audit separately from report content.

20. Acceptance tests
• Only one active 72-hour link per report; revoke/expire/finalise prevents editing; replacement link only after invalidation.
• Original snapshot/files never change after any desktop edit, mobile sync or finalisation.
• One current edited report; successful save increments version and audit captures before/after.
• Two sessions: first save succeeds; stale second receives 409 and unsaved changes remain recoverable.
• Phone unsent changes are not silently overwritten; stale mobile push is rejected and surfaced.
